# 延遲:時間花在哪、怎麼變快

2026-10-21 開始。這份先寫好「為什麼做」和「實驗設計」再跑實驗,結果依日期往下加。含實際聽寫內容的原始資料放在私人 repo `voiceink-zhtw-data` 的 `2026-10-21-latency/`,這裡只放統計數字。

## 背景

v2 用起來覺得從放開快捷鍵到文字貼上太慢。2026-10-21 的 VoiceInk 紀錄(M1 Pro 32GB,補標點模型已載入):

| 講多久 | 語音辨識 | 補標點 | 合計(含貼上約 0.3 秒) |
|---|---|---|---|
| 3 秒短句 | 1.2–1.4 秒 | 0.8–1.0 秒 | 約 2.5 秒 |
| 30 秒 | 3.5–5 秒 | 2.5–4.5 秒 | 約 6.5–10 秒 |
| 1 分鐘 | 8.1 秒 | 7.1 秒 | 約 15.5 秒 |

- **語音辨識**:Whisper 類模型不管講多短都處理一整段 30 秒的音訊,短句最少約 1.2 秒;長句約是講話時間的 1/8。
- **補標點**:語言模型把整段字重新產生一次,越長越久(約每 100 字 1.3–2.7 秒)。講長一點時和語音辨識差不多慢。

另外發現**補標點偶爾多約 1.5 秒**:15:57 重開 App 後的 14 次聽寫,跟上一句隔不到 1 分鐘的 6 次全部變慢,隔超過 1 分鐘的 8 次全部正常。已排除:

- 模型被卸載:負責補標點的 XPC 子程序從啟動後一直常駐(約 2.2GB)。
- 模型多吐字:用 LM Studio 以同一個模型、指示、temperature 0 重跑變慢的句子,只輸出 13–14 個 token 就停。

要回答兩個問題:**(1) 多出來的 1.5 秒卡在哪?(2) 整體怎麼變快?**

## 量測方式

VoiceInk 原本就有的:紀錄資料庫的錄音長度、辨識耗時、潤稿耗時;系統紀錄裡有辨識開始和結束、貼上的時間。

新增計時(系統紀錄,subsystem `com.prakashjoshipax.voiceink`、category `ZhTWTiming`,**只記時間和數量,不記內容**):

| 位置 | 記錄 |
|---|---|
| App:`VoiceInkRefineXPCClient` | 等前一個動作做完(排隊)的時間、XPC 來回總時間 |
| App:`VoiceInkRefineService` | 合併標點的耗時、字數 |
| XPC:`VoiceInkRefineXPCService` | 收到請求到回覆的總時間 |
| XPC:`VoiceInkRefineInferenceEngine` | 準備模型(已載入或重新載入)、讀入指示的 token 數和耗時、產生的 token 數和耗時、停止原因、距離上一次補標點的閒置秒數、系統溫度狀態、低耗電模式 |

`scripts/timing_report.py` 把系統紀錄整理成「每次聽寫一行」的表(錄音、間隔、辨識、排隊、讀入指示、產生文字、貼上…)。實驗 A 期間另外每 0.5 秒記一次 GPU 使用率和最吃 CPU 的程序(`scripts/bench/sample_load.py`),用來看變慢時有沒有別的東西在搶資源;`timing_report.py --load` 會把錄音期間的負載對到每一行。

## 實驗設計

### A. 補標點偶爾多 1.5 秒

事先列出的可能原因:

1. 上一句之後約 1 分鐘內,有別的東西在用 GPU 或 CPU(VoiceInk 自己的後續處理、貼上的目標 App、其他程式)。
2. 在排隊等前一個動作(例如錄音開始時的準備)。
3. 系統降頻(溫度、低耗電模式)。
4. 不是排隊,而是讀入指示或產生文字本身變慢(要從計時分辨是哪一段)。

做法:

- 加計時、重 build、安裝。
- 用 8 句自編、長度相近(約 13 字)的短句,貼到「文字編輯」(不貼到 Claude,先排除目標 App 的影響)。依序隔 10 秒、30 秒、60 秒、120 秒各講兩次。測試期間不跑其他耗資源的工作。
- 判讀:
  - 隔 1 分鐘內仍然變慢 → 看計時慢在哪一段,對照同時間的 GPU、CPU 紀錄。
  - 在「文字編輯」不會變慢 → 改貼到 Claude 的輸入框再測一輪,確認是不是目標 App 造成的。

### B. 語音辨識加速

- **資料**:這台 VoiceInk 存的錄音(58 段,約 24MB)。原始檔和逐句結果複製到私人 repo。
- **工具**:用 VoiceInk 同版本的 whisper.cpp 編命令列工具離線跑。語言、提示詞、解碼參數照 VoiceInk 實際用的設定(實作時從程式查清楚,記在結果裡)。
- **比較的組合**:
  - f16:最大、最準,當作**參考答案**。
  - q8_0:現在用的。
  - q5_0、q4_k:更小的量化。
  - q8_0 + Core ML 編碼器:轉檔者有提供 Breeze 的 Core ML 檔,可以用 Apple 的神經引擎。
- **指標**:
  - 速度:每段耗時,分短(5 秒以下)、中、長三組。每個組合跑兩次取第二次(第一次含載入);Core ML 第一次編譯的時間另外記。
  - 準確度:和 f16 比的字元錯誤率(CER)。不一樣的句子先由 Sonnet 子代理逐句判斷「意思有沒有變」,Claude 複核,還有疑慮的再請使用者確認。
- 跑的時候不要聽寫(會搶 GPU,也會讓實驗 A 的計時失真)。

### C. 補標點加速

- **資料**:同一批錄音在 VoiceInk 裡的辨識結果(沒有標點的原文)。
- **比較的對象**:
  - Breeze2-3B:現在用的。速度以實驗 A 在 App 裡量到的為準。
  - 專門的中文標點模型,例如 FunASR 的 CT-Transformer:整段只看一次,只判斷字和字之間要不要加標點,結構上不會改字。其他候選實作時再查。
- 專門的標點模型多半用簡體訓練:先轉簡體給它判斷,再把標點插回繁體原文(和現在的合併邏輯同一套)。
  - Breeze2-3B + 固定指示先算好重複用(根據實驗 A 新增):只改速度,輸出應該和現在完全一樣。
- **指標**:
  - 耗時:分短、中、長三組。
  - 標點品質:約 15 句盲測,使用者看兩個版本但不知道哪個是哪個,選比較好的。先由 Sonnet 子代理挑出兩邊差異明顯的句子。
  - 放進 App 的工作量:ONNX Runtime 或轉成 Core ML。

## 結果

### A. 補標點偶爾多 1.5 秒(2026-10-21)

**原因:模型被卸載又重新載入,和間隔、負載都無關。** 事先列的 4 個可能原因都不是。

照設計測了 11 句(第 0 句暖機不算)。原始計時表在私人 repo 的 `A-timing-run1.txt`(只有數字):

| | 句數 | 補標點前的準備 | XPC 來回 | 放開快捷鍵到貼上 |
|---|---|---|---|---|
| 補標點時重新載入模型 | 6 | 1.64–1.68 秒(載入 0.9 + 暖機 0.7) | 2.44–2.66 秒 | 3.94–4.34 秒 |
| 沒有重新載入 | 5 | 0 | 0.83–0.96 秒 | 2.32–2.54 秒 |

- 變慢的 6 句,和上一句的間隔從 20 秒到 135 秒都有;正常的 5 句也是 7 秒到 122 秒都有。**之前看到「1 分鐘內就變慢」是樣本少的巧合。**
- 排隊 0 秒、溫度狀態一直是正常、執行優先度都是 userInitiated;錄音期間沒有其他程式明顯搶資源。
- 另外 3 句的重新載入發生在錄音開始時(藏在講話的時間裡,感覺不到,但白白多用 GPU)。

**為什麼會重新載入**:XPC 引擎比對「這次的指示」和「模型準備好時的指示」,不一樣就卸載重來。指示是 `ZhTWPunctuation.encodedInstructions` 把 Swift 字典轉成 JSON,而 Swift 字典每次建立時 key 的順序可能不同(小程式實測:同樣的字典建 200 次,兩種順序分別出現 192 次和 8 次)。所以有時候字串不一樣,模型就被重新載入。

**修正**:指示只算一次、key 固定排序(commit `f653db2`)。修正後的驗證見下面。

**順便量到的**:沒有重新載入時,補標點的 0.9 秒裡有 0.64–0.71 秒花在讀入約 350 個 token,其中約 330 個是固定的指示和範例,每次都重讀;產生文字只要 0.11–0.25 秒(8–19 個 token)。把固定部分先算好重複用,短句的補標點有機會降到約 0.3 秒。加進實驗 C 一起評估。

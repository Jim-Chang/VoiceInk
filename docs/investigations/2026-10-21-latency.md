# 延遲:時間花在哪、怎麼變快

2026-10-21 開始。這份先寫好「為什麼做」和「實驗設計」再跑實驗,結果依日期往下加。含實際聽寫內容的原始資料放在私人 repo `voiceink-zhtw-data` 的 `2026-10-21-latency/`,這裡只放統計數字。

## 背景

v2 用起來覺得從放開快捷鍵到文字貼上太慢。2026-10-21 的 VoiceInk 紀錄(M1 Pro 32GB,補標點模型已載入):

| 講多久 | 語音辨識 | 補標點 | 合計(含貼上約 0.3 秒) |
|---|---|---|---|
| 3 秒短句 | 1.2–1.4 秒 | 0.8–1.0 秒 | 約 2.5 秒 |
| 30 秒 | 3.5–5 秒 | 2.5–4.5 秒 | 約 6.5–10 秒 |
| 1 分鐘 | 8.1 秒 | 7.1 秒 | 約 15.5 秒 |

- **語音辨識**:Whisper 類模型不管講多短都處理一整段 30 秒的音訊,短句最少約 1.2 秒;長句約是講話時間的 1/8。
- **補標點**:語言模型把整段字重新產生一次,越長越久(約每 100 字 1.3–2.7 秒)。講長一點時和語音辨識差不多慢。

另外發現**補標點偶爾多約 1.5 秒**:15:57 重開 App 後的 14 次聽寫,跟上一句隔不到 1 分鐘的 6 次全部變慢,隔超過 1 分鐘的 8 次全部正常。已排除:

- 模型被卸載:負責補標點的 XPC 子程序從啟動後一直常駐(約 2.2GB)。
- 模型多吐字:用 LM Studio 以同一個模型、指示、temperature 0 重跑變慢的句子,只輸出 13–14 個 token 就停。

要回答兩個問題:**(1) 多出來的 1.5 秒卡在哪?(2) 整體怎麼變快?**

## 量測方式

VoiceInk 原本就有的:紀錄資料庫的錄音長度、辨識耗時、潤稿耗時;系統紀錄裡有辨識開始和結束、貼上的時間。

新增計時(系統紀錄,subsystem `com.prakashjoshipax.voiceink`、category `ZhTWTiming`,**只記時間和數量,不記內容**):

| 位置 | 記錄 |
|---|---|
| App:`VoiceInkRefineXPCClient` | 等前一個動作做完(排隊)的時間、XPC 來回總時間 |
| App:`VoiceInkRefineService` | 合併標點的耗時、字數 |
| XPC:`VoiceInkRefineXPCService` | 收到請求到回覆的總時間 |
| XPC:`VoiceInkRefineInferenceEngine` | 準備模型(已載入或重新載入)、讀入指示的 token 數和耗時、產生的 token 數和耗時、停止原因、距離上一次補標點的閒置秒數、系統溫度狀態、低耗電模式 |

`scripts/timing_report.py` 把系統紀錄整理成「每次聽寫一行」的表(錄音、間隔、辨識、排隊、讀入指示、產生文字、貼上…)。實驗 A 期間另外每 0.5 秒記一次 GPU 使用率和最吃 CPU 的程序(`scripts/bench/sample_load.py`),用來看變慢時有沒有別的東西在搶資源;`timing_report.py --load` 會把錄音期間的負載對到每一行。

## 實驗設計

### A. 補標點偶爾多 1.5 秒

事先列出的可能原因:

1. 上一句之後約 1 分鐘內,有別的東西在用 GPU 或 CPU(VoiceInk 自己的後續處理、貼上的目標 App、其他程式)。
2. 在排隊等前一個動作(例如錄音開始時的準備)。
3. 系統降頻(溫度、低耗電模式)。
4. 不是排隊,而是讀入指示或產生文字本身變慢(要從計時分辨是哪一段)。

做法:

- 加計時、重 build、安裝。
- 用 8 句自編、長度相近(約 13 字)的短句,貼到「文字編輯」(不貼到 Claude,先排除目標 App 的影響)。依序隔 10 秒、30 秒、60 秒、120 秒各講兩次。測試期間不跑其他耗資源的工作。
- 判讀:
  - 隔 1 分鐘內仍然變慢 → 看計時慢在哪一段,對照同時間的 GPU、CPU 紀錄。
  - 在「文字編輯」不會變慢 → 改貼到 Claude 的輸入框再測一輪,確認是不是目標 App 造成的。

### B. 語音辨識加速

- **資料**:這台 VoiceInk 存的錄音(58 段,約 24MB)。原始檔和逐句結果複製到私人 repo。
- **工具**:用 VoiceInk 同版本的 whisper.cpp 編命令列工具離線跑。語言、提示詞、解碼參數照 VoiceInk 實際用的設定(實作時從程式查清楚,記在結果裡)。
- **比較的組合**:
  - f16:最大、最準,當作**參考答案**。
  - q8_0:現在用的。
  - q5_0、q4_k:更小的量化。
  - q8_0 + Core ML 編碼器:轉檔者有提供 Breeze 的 Core ML 檔,可以用 Apple 的神經引擎。
- **指標**:
  - 速度:每段耗時,分短(5 秒以下)、中、長三組。每個組合跑兩次取第二次(第一次含載入);Core ML 第一次編譯的時間另外記。
  - 準確度:和 f16 比的字元錯誤率(CER)。不一樣的句子先由 Sonnet 子代理逐句判斷「意思有沒有變」,Claude 複核,還有疑慮的再請使用者確認。
- 跑的時候不要聽寫(會搶 GPU,也會讓實驗 A 的計時失真)。

### C. 補標點加速

- **資料**:同一批錄音在 VoiceInk 裡的辨識結果(沒有標點的原文)。
- **比較的對象**:
  - Breeze2-3B:現在用的。速度以實驗 A 在 App 裡量到的為準。
  - 專門的中文標點模型,例如 FunASR 的 CT-Transformer:整段只看一次,只判斷字和字之間要不要加標點,結構上不會改字。其他候選實作時再查。
- 專門的標點模型多半用簡體訓練:先轉簡體給它判斷,再把標點插回繁體原文(和現在的合併邏輯同一套)。
  - Breeze2-3B + 固定指示先算好重複用(根據實驗 A 新增):只改速度,輸出應該和現在完全一樣。
- **指標**:
  - 耗時:分短、中、長三組。
  - 標點品質:約 15 句盲測,使用者看兩個版本但不知道哪個是哪個,選比較好的。先由 Sonnet 子代理挑出兩邊差異明顯的句子。
  - 放進 App 的工作量:ONNX Runtime 或轉成 Core ML。

## 結果

### A. 補標點偶爾多 1.5 秒(2026-10-21)

**原因:模型被卸載又重新載入,和間隔、負載都無關。** 事先列的 4 個可能原因都不是。

照設計測了 11 句(第 0 句暖機不算)。原始計時表在私人 repo 的 `A-timing-run1.txt`(只有數字):

| | 句數 | 補標點前的準備 | XPC 來回 | 放開快捷鍵到貼上 |
|---|---|---|---|---|
| 補標點時重新載入模型 | 6 | 1.64–1.68 秒(載入 0.9 + 暖機 0.7) | 2.44–2.66 秒 | 3.94–4.34 秒 |
| 沒有重新載入 | 5 | 0 | 0.83–0.96 秒 | 2.32–2.54 秒 |

- 變慢的 6 句,和上一句的間隔從 20 秒到 135 秒都有;正常的 5 句也是 7 秒到 122 秒都有。**之前看到「1 分鐘內就變慢」是樣本少的巧合。**
- 排隊 0 秒、溫度狀態一直是正常、執行優先度都是 userInitiated;錄音期間沒有其他程式明顯搶資源。
- 另外 3 句的重新載入發生在錄音開始時(藏在講話的時間裡,感覺不到,但白白多用 GPU)。

**為什麼會重新載入**:XPC 引擎比對「這次的指示」和「模型準備好時的指示」,不一樣就卸載重來。指示是 `ZhTWPunctuation.encodedInstructions` 把 Swift 字典轉成 JSON,而 Swift 字典每次建立時 key 的順序可能不同(小程式實測:同樣的字典建 200 次,兩種順序分別出現 192 次和 8 次)。所以有時候字串不一樣,模型就被重新載入。

**修正**:指示只算一次、key 固定排序(commit `f653db2`)。

**修正後驗證**:重開 App 後連續聽寫 12 句(10 句短句間隔約 10 秒,另有 10 秒、37 秒各一句),**只在第一句錄音開始時載入一次模型**(藏在講話時間裡),之後全部沒有重新載入。短句的補標點 0.77–1.01 秒,放開快捷鍵到貼上 2.24–2.65 秒。原始計時表在私人 repo 的 `A-timing-run2-after-fix.txt`。

**順便量到的**:沒有重新載入時,補標點的 0.9 秒裡有 0.64–0.71 秒花在讀入約 350 個 token,其中約 330 個是固定的指示和範例,每次都重讀;產生文字只要 0.11–0.25 秒(8–19 個 token)。把固定部分先算好重複用,短句的補標點有機會降到約 0.3 秒。加進實驗 C 一起評估。

**討論後的結論(2026-10-21)**:修好字串之後還有兩個設計問題,先修再做 B、C。

1. **換指示不需要重新載入模型。** 模型權重和指示無關;原作者的引擎把「模型 + 指示」綁成一組準備好的狀態,指示一變就整組丟掉重來。原作者的指示是寫死的,永遠不會變,所以他們不會付出這個代價。改成只有換模型資料夾才卸載;只換指示時模型留著,重算下面的 prefix cache。
2. **固定的指示和範例應該用 prefix cache。** 原作者的「暖機」只是載入後讓 GPU 先跑一次,算完的結果沒有留下來;每句都重讀約 330 個 token。MLX 函式庫支援把共用的開頭算成 KV cache、每次複製一份接著算(`KVCache.copy()`、`generate(input:cache:…)`)。

另外使用者回報**講很長時沒有標點**:582 字的一段,模型只輸出 33 個 token 就停了(把整段當成要回應的話),合併對不上就整段退回原文。改成長的逐字稿分段補(見 C 的結果)。

### B. 語音辨識加速(2026-10-21)

資料:這台 VoiceInk 存的 91 段錄音(5 秒以下 51 段、5–20 秒 28 段、20 秒以上 12 段)。用 VoiceInk 同版本的 whisper.cpp(Metal + Core ML)編 `whisper-cli`,參數照 App(中文、使用者的繁體提示詞、greedy、temperature 0.2、best_of 5、8 執行緒、flash attention、silero VAD)。每段各開一次程式,「辨識時間」= 總時間 − 載入時間(App 在錄音開始時載入,藏在講話時間裡)。原始結果在私人 repo 的 `B-results.json`。

| 版本 | 檔案大小 | 和 f16 比的字元錯誤率 | 和 f16 完全相同 | 辨識時間中位數 短 / 中 / 長 | 91 段合計 | 載入 |
|---|---|---|---|---|---|---|
| f16(參考答案) | 3.1GB | — | — | 1.18 / 1.80 / 4.92 秒 | 181.8 秒 | 1.00 秒 |
| **q8_0(現在用的)** | 1.66GB | 0.33% | 86/91 | 1.21 / 1.76 / 4.68 秒 | 177.2 秒 | 0.51 秒 |
| q5_0 | 1.08GB | 1.59% | 70/91 | 1.36 / 1.98 / 5.30 秒 | 199.7 秒 | 0.34 秒 |
| q4_k | 0.89GB | 2.59% | 56/91 | 1.30 / 1.88 / 5.00 秒 | 189.2 秒 | 0.29 秒 |
| q8_0 + Core ML 編碼器 | 1.66GB + 1.2GB | 0.65% | 79/91 | 1.90 / 2.48 / 6.25 秒 | 253.0 秒 | 0.52 秒 |

和 f16 不同的句子由 Sonnet 子代理逐句判讀(私人 repo 的 `B-review-sonnet.json`):

| 版本 | 和 f16 不同 | 意思不變(同音字、語助詞等) | 小錯字 | 意思改變 |
|---|---|---|---|---|
| q8_0 | 5 段 | 3 | 1 | 1(f16 那段本身也不通順,判斷不出誰對) |
| q5_0 | 21 段 | 9 | 11 | 1 |
| q4_k | 35 段 | 15 | 12 | 8 |
| q8_0 + Core ML | 12 段 | 6 | 4 | 2 |

離線的 whisper-cli 偶爾會在結尾留下特殊標記(例如 `<|5.59|>`),判讀時不算錯;App 的紀錄裡沒有出現過。

- **更小的量化沒有變快,反而錯得比較多。** 在 M1 Pro 的 GPU(Metal)上,辨識時間主要花在計算,不是讀取模型,q5、q4 反而略慢。
- q8 和 f16 幾乎一樣(91 段只有 5 段不同),現在用 q8 是對的。
- **Core ML(Apple 神經引擎)更慢**:編碼器中位數 1.45 秒,Metal 是 0.86 秒;而且每台 Mac 第一次要先編譯 871 秒(14.5 分鐘)。不採用。VoiceInk 的 whisper.cpp 有開 Core ML,只要編碼器檔案放在模型旁邊就會自動使用,所以**不要**把轉檔者提供的 `ggml-breeze-asr-25-encoder.mlmodelc` 放進 `WhisperModels/`。
- 短句的 1.2 秒裡,編碼器佔 0.86 秒:Whisper 不管講多短,編碼器都處理一整段 30 秒的音訊。

看完上面的結果後追加的兩個測試(不在原本的設計裡):

- **重跑一次 q8**:91 段和第一次完全相同,離線辨識是確定的;q8 和 f16 的 0.33% 差異是模型本身的差異,不是抽樣雜訊。
- **讓編碼器只處理錄音實際的長度**(whisper.cpp 的 `audio_ctx`,25 秒以下的 81 段):短句的辨識從 1.18 秒降到 0.48 秒,但和 f16 比的字元錯誤率變成約 20%,81 段裡 17 段錯超過三成(Breeze 是微調過的模型,只看過完整的 30 秒)。**不採用。**
- 離線的 q8 和 App 當時的結果不完全相同(整體約 5% 的字不同):App 辨識的是錄音當下的音訊資料、檔案是存檔後的版本,temperature 0.2 會抽樣,對極小的輸入差異很敏感;較早的錄音也是用舊的提示詞辨識的。各版本之間的比較用的是同一份檔案、同一組參數,不受影響。

### C. 補標點加速(2026-10-21)

資料:這台 VoiceInk 存的 91 段實際聽寫的辨識結果(短句 ≤20 字 47 段、中 21–120 字 31 段、長 >120 字 13 段,最長 582 字)。Breeze2 用 `scripts/bench/refine-bench.sh` 跑(編譯 App 裡同一份引擎和合併程式,離線、M1 Pro);CT-Transformer 用 sherpa-onnx 1.13.8(CPU)。原始輸出在私人 repo 的 `C-*.json`。

**速度**(每段補標點的時間,中位數 / 最大):

| | 短句 | 中 | 長 |
|---|---|---|---|
| Breeze2,原作者做法(每句重讀指示) | 0.82 / 0.98 秒 | 1.25 / 1.99 秒 | 2.90 / 5.54 秒 |
| Breeze2 + prefix cache | 0.26 / 0.36 秒 | 0.70 / 1.39 秒 | 2.36 / 5.16 秒 |
| Breeze2 + prefix cache + 分段(App 現在的做法) | 0.26 / 0.37 秒 | 0.70 / 1.39 秒 | 2.70 / 9.78 秒 |
| CT-Transformer,1 執行緒 | 2.8 / 4.1 毫秒 | 9.4 / 19.6 毫秒 | 46 / 153 毫秒 |
| CT-Transformer,4 執行緒 | 1.4 / 1.9 毫秒 | 4.0 / 7.9 毫秒 | 18 / 58 毫秒 |

**Breeze2 + prefix cache 的輸出**:91 段裡 89 段和原作者做法逐字相同;另外 2 段有幾個逗號、問號的位置不同(計算拆成前段、後段兩次,浮點數有極小差異,模型在兩個選擇幾乎打平時偶爾選另一個),兩邊都通順,字完全一樣。

**分段**:每段最多 120 字。兩段原本整段沒有標點的長句(582 字、135 字)現在有了;長句的中位數多約 0.3 秒(每段尾巴重算)。寫測試時發現一個問題:切在句子中間時,模型會在段尾補「。」,第一版把它當成句尾收進來;改成段尾的標點不算(commit `babd2f6`)。

**CT-Transformer**(FunASR 的中英文標點模型,sherpa-onnx 轉成 ONNX,模型 294MB):

- 用簡體訓練。先把繁體轉簡體給它,再用 App 的合併邏輯把標點插回繁體原文。直接給繁體也能用,但問號少很多(46 個 vs 55 個)。
- 和 Breeze2(分段)比:標點總數 442 vs 456、問號 55 vs 57、91 段裡 31 段完全相同。結構上只判斷字和字之間要不要加標點,不會改字、不會把逐字稿當成問題來回答,也不需要分段。
- 載入 0.2 秒,只用 CPU,不和語音辨識搶 GPU。
- 放進 App 的工作量:要加 ONNX Runtime(sherpa-onnx 有 C API 和 macOS 的 xcframework),新寫一條補標點的路徑取代 VoiceInk Refine。
- **int8 量化版**(模型 75MB):91 段裡 80 段和原版完全相同,標點數 445 vs 442、問號 56 vs 55;短句 2.0 毫秒、長句中位 34 毫秒(1 執行緒)。要放進 App 的話用這個版本。

**標點品質**:兩邊合併結果不同的 56 段,由 Sonnet 子代理盲評(每段 A、B 隨機對應,不知道哪邊是哪個模型):

| | Breeze2 較好 | CT-Transformer 較好 | 差不多 |
|---|---|---|---|
| 短句(15 段) | 7 | 2 | 6 |
| 中(28 段) | 9 | 12 | 7 |
| 長(13 段) | 0 | 8 | 5 |
| 合計 | 16 | 22 | 18 |

短句 Breeze2 好一些,長句 CT-Transformer 明顯好。從中挑了 15 題(短 5、中 7、長 3)給使用者盲測:私人 repo 的 `C-blind-test.md`,答案在 `C-blind-key.json`。

**使用者盲測(2026-10-22)**:每題只看到 A、B,不知道哪邊是哪個模型;「差不多」不代表兩邊都好或都不好。逐題結果在私人 repo 的 `C-blind-result.json`。

**在 App 裡的驗證(2026-10-21 晚上到 10-22,`scripts/timing_report.py`)**:裝了 prefix cache 之後的 3 次聽寫都是 `pfx=1`,讀入的 token 從 379–621 個降到 27–76 個。
